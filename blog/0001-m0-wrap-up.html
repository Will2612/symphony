M0 收尾 — Swift 6 运行时壳落地

M0 of 5 · 2026-06-14 · Symphony Swift 端口 · Will2612/symphony

M0 没用一行业务代码，只为后续 M1–M4 铺好 Swift 6 工具链、容器化、和 GHCR 发布这条通路。 跑完这一步，docker pull ghcr.io/will2612/symphony:dev && docker run --rm ... --version 应该可工作。

这是 5 篇里程碑博客中的第 1 篇。M0 = Swift 6 运行时壳：CLI + 多架构 Docker + GitHub Actions + GHCR 发布。 业务逻辑（Configuration、Tracker、Orchestrator、Worker 协议）一律留给 M1–M4。 本篇按"是什么 → 踩了什么坑 → 物证 → 决策 → 下集预告"的顺序展开。

1. M0 是什么 & 不是什么

M0 = 8 个文件，加起来 230 行，能让一个 Swift 6 进程以 symphony 之名在 amd64 与 arm64 容器里跑起来、对外报版本与帮助、然后干净退出。三个 feature：

  1. CLI shell：--version / --help，错误时退 64（BSD sysexits EX_USAGE）
  2. 多阶段 Dockerfile：builder 装 swift:6.3.2-noble + 缓存挂载，runtime 切到 swift:6.3.2-noble-slim + 非 root（UID 10001）
  3. CI：每次 swift-implementation 推 commit 或 v* tag，GitHub Actions 单 job + QEMU 交叉编译，构建多架构镜像推到 ghcr.io/will2612/symphony

M0 不做：不读 WORKFLOW.md、不发任何 HTTP 请求、不接 codex 也不接 opencode、不轮询任何 tracker。 那些是 M1、M2、M3 的事。M0 是一根干净的零号管线——通了之后再加支路。

整个 M0 期间 0 第三方 Swift 依赖（Package.swift 至今只有 stdlib + Foundation）。下一里程碑才考虑加 Yams、swift-argument-parser、swift-log。

2. 8 个产物

每个文件一段。行号引用指向 swift-implementation 分支当前状态（commit a6c23b8）。

Package.swift — 13 行

swift-tools-version: 6.3，单个 executableTarget(name: "Symphony")，platforms: [.macOS(.v14)]。 没有 path: 也没有第三方依赖——Sources/Symphony/main.swift 由 SPM 默认约定解析。 460b802 把 tools-version 从 6.0 升到 6.3（与运行时基础镜像 swift:6.3.2-noble 对齐）， 同时把冗余的 path: "Sources/Symphony" 行删了。

Sources/Symphony/main.swift — 39 行

import Foundation，4 个常量（version、swiftVersion、argv、exeName），两个打印函数，一个 guard 拦无参，一个 switch 分发 --version/-v / --help/-h / 未知项退 64。 版本号硬编码在文件顶部——不接 git describe（M0 阶段不需要版本自动化）。 87c0dbb 删了 help 末尾指向 SPEC.md 与 Plan.md 的死链（runtime 容器里没这俩文件）。

deploy/Dockerfile — 18 行

两阶段：builder 用 --platform=$TARGETPLATFORM（非 $BUILDPLATFORM，见 §3）， --mount=type=cache 把 /root/.cache/swift 与 /build/.build 挂出去加速冷构建。 runtime 切到 -slim 镜像，useradd -m -u 10001 symphony，USER symphony。 196be8f 在 runtime 阶段也加了 --platform=$TARGETPLATFORM（虽然 BuildKit 默认已经按 target platform 解析，显式写出来防止未来 BuildKit 改默认）， 顺带建了仓根的 .dockerignore——把 .git、.github、各种 .md 排除在构建上下文外，冷构建上下文从 ~30MB 缩到几百 KB。

deploy/docker-compose.yml — 13 行

name: symphony，单服务，context: ..（compose 文件本身在 deploy/ 里，. 会解析到 deploy/，d1fb1df 改回仓根）， image: ghcr.io/will2612/symphony:dev，command: ["--version"]，restart: "no"。 bind mount ./repos 和 ./logs 在 M0 阶段只占位，compose up 跑完就退，验证管线通畅。

deploy/.env.example — 15 行

纯文档桩。M0 不消费任何环境变量。三个 section：OPENAI_API_KEY（M2+ codex worker 专用）、 GITHUB_TOKEN / GITHUB_PROJECT_OWNER / GITHUB_PROJECT_NUMBER（M1+ GitHub Projects）、 OPENCODE_HOST/PORT（M2+ 默认 worker opencode/ACP）和 CODEX_HOST/PORT（M2+ 可选 worker codex v2 JSON-RPC）。 2d33e99 补了 OPENCODE 段以对齐 MISSION 里"opencode 是默认 worker"的决定， 同时把 .env / .env.* 加进 .gitignore，避免用户复制 .env.example 时意外 commit。

.github/workflows/release.yml — 67 行

单 job + QEMU，不是 per-arch matrix。触发条件：push branches: [swift-implementation]、 push tags: ['v*']、workflow_dispatch。 6 个 uses: 全 SHA-pin（actions/checkout@34e1148 等等），行尾注释标版本号，Elixir 仓的 supply-chain 约定。 docker/metadata-action 配 flavor: latest=false，输出三种 tag： :dev（branch + tag push 都出，指向最新）、:vX.Y.Z（仅 semver tag）、:sha-abc1234（所有 push）。 provenance: false + sbom: false 关掉 buildkit 的 SLSA attestation 副作用。 d3402a7 钉 SHA + 改 {{raw}}（保留 v） + 禁 :latest； b43988f 加 branch trigger + :sha tag； 0a09870 把 per-arch matrix 换成单 job + QEMU（见 §3）； 8216270 关 attestations。

.gitignore — 11 行

Swift 标准（.build/、.swiftpm/、*.xcodeproj）+ 项目特定（repos/、logs/、workspaces/）+ .env*。 不忽略 Package.resolved（6ce820a 改的）——SPM lockfile 跟 Elixir 的 mix.lock 一样 commit， M1+ 引入第三方 Swift 依赖时这条策略就生效。

README.md — 35 行

两段定位（"长跑守护进程" + "Swift 端口"）、一个 quick-start 代码块、三个链接（Plan.md、SPEC.md、教学仓）、Apache 2.0 license。 quick-start 写的是 docker run --rm ghcr.io/will2612/symphony:dev --version——M0 收尾前这个命令真的会工作（见 §4）。

3. 关键修正（Plan → Code 偏差）

M0 收尾时回看，发现实施过程中 Plan §3 的 3 段草案与实际代码有 4 处偏差，外加 review 阶段又抓出 1 个真 bug。其中 3 个是"Plan 写错"——值得给未来的自己留个标记。

偏差 1：BuildKit cache mount 不可见 (2395a20)

Plan §3.5 草案直接 COPY --from=builder /build/.build/release/symphony /usr/local/bin/symphony，但 --mount=type=cache,target=/build/.build 挂的是 cache mount，只在那个 RUN 指令期间存在， 后续 FROM 看不到。修法是先 cp /build/.build/release/symphony /symphony 把产物拷出 mount， 再 COPY --from=builder /symphony。

偏差 2：compose build context 解析 (d1fb1df)

Plan §3.6 草案 context: .，但 compose 文件本身就在 deploy/ 里，. 解析成 deploy/， 接着 dockerfile: deploy/Dockerfile 就会去找 deploy/deploy/Dockerfile——不存在。 改 context: .. 回到仓根。这是经典的"相对路径相对哪里"陷阱。

偏差 3：$BUILDPLATFORM vs $TARGETPLATFORM (aa83346)

Plan §3.5 草案 FROM --platform=$BUILDPLATFORM，逻辑是"在什么架构上跑 build"。但 Swift **没有原生跨编译**—— Package.swift 的 platforms: [.macOS(.v14)] 不触发 Linux 跨编译， 也没法在 amd64 runner 上原生 build arm64。修正为 $TARGETPLATFORM，搭配 QEMU 做 arm64 模拟（见偏差 4）。 这个差异用 file /symphony 一行命令就抓出来了——最初 build 出来是 x86-64，不是 aarch64。

偏差 4：per-arch matrix 同 tag 后写覆盖前写 (0a09870)

最初设计是 per-arch matrix：两个 job 分别跑在 ubuntu-latest (amd64) 和 ubuntu-24.04-arm (arm64) 上， 各自 build 单架构镜像，推同一个 tag。结果：哪个 job 后完成哪个赢，GHCR 里只剩一个架构 + 一个 buildkit provenance attestation。 验证命令 docker manifest inspect ghcr.io/will2612/symphony:sha-b43988f 返回 arm64 + unknown——amd64 manifest 被覆盖了。修法是单 job + --platform linux/amd64,linux/arm64， buildx 一次性出多架构 OCI image index。arm64 走 QEMU 模拟，比 native 慢 5-10 倍，但跑得通。

Review 抓出的小坑（已修）

在 file-by-file review（每个文件 1 个 commit）阶段还修了几处：

  • 460b802：swift-tools-version 6.0 → 6.3；删 path: "Sources/Symphony" 冗余行
  • 87c0dbb：删 help 文本里指向 SPEC.md/Plan.md 的死链
  • d3402a7：所有 uses: SHA-pin + 改 {{raw}} 保留 v 前缀 + flavor: latest=false
  • 6ce820a：Package.resolved 改为 commit（匹配 Elixir mix.lock 策略）

4. CI 端到端跑通的物证

最关键的事：我能不能真的拉到这个 image 并跑起来？能。commit 8216270 之后我做了四次验证：

$ docker pull --quiet ghcr.io/will2612/symphony:dev
ghcr.io/will2612/symphony:dev
$ docker run --rm ghcr.io/will2612/symphony:dev --version
symphony 0.0.0-dev (swift 6.3.2)

$ docker manifest inspect ghcr.io/will2612/symphony:dev \
    | jq -c '.manifests[] | {arch: .platform.architecture, os: .platform.os, bytes: .size}'
{"arch":"amd64","os":"linux","bytes":1489}
{"arch":"arm64","os":"linux","bytes":1489}

$ gh run list --repo Will2612/symphony --workflow=release --limit 1
completed  success  8216270  swift-implementation  38s

三件事值得拎出来：

  1. manifest 干净。只有 amd64 + arm64，没有 architecture: unknown 幽灵。 那是 buildkit 默认会塞进来的 SLSA provenance attestation（每个 arch 1 个），用 provenance: false + sbom: false 关掉。开了会更"SLSA Level 3 合规"，但 GHCR UI 里看着像 4 个平台，困惑大于价值。M4 收尾时再开。
  2. CI 跑了 38 秒，因为命中 GHA cache。 冷构建第一次（commit b43988f）是 4 分 13 秒——主要时间花在装 Swift 6.3.2 toolchain（~1.5 分钟）和首次 swift build（~2.5 分钟）。 之后每次 push，cache 命中，build 阶段 ~30 秒。
  3. 没有跑过 semver tag 路径。所有验证都是 branch push；{{raw}} + {{semver}} 在 metadata-action 配置里结构同源，但 真推一个 v0.0.0-dev tag 才会触发 :v0.0.0-dev tag 的产出。M1 启动时我会推一次作为冒烟。
想看 CI 现场：github.com/Will2612/symphony/actions?query=workflow:release。

想直接拉镜像：docker pull ghcr.io/will2612/symphony:dev。

6. M1 入口

M1 = Configuration + Tracker。M1 收尾时 daemon 应当：

  1. 能读 WORKFLOW.md（YAML front matter + prompt 模板）→ WorkflowLoader.swift
  2. 能解析 env + 校验 + 动态 reload → Config.swift
  3. 能从 GitHub Projects v2 拉 issue → Tracker 协议 + GitHubProjectsV2Tracker（+ 测试用 MemoryTracker）
  4. 能渲染 prompt（strict variables + strict filters，§12 规则）
  5. 能写结构化日志 → StructuredLogger
  6. Issue 领域模型 + 归一化规则（§11.3）

对位 SPEC §5、§6、§11、§12、§13.1。M1 不做 orchestrator、worker 协议、workspace、retry、stall、reconciliation——那些是 M2/M3。 仍不调度、不发 agent——daemon 知道要做什么，但还不会做。
